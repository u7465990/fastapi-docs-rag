## 1. 检索评估：先知道现在到底好不好

### 1.1 为什么先做评估

如果先加 SSE、多轮、rerank，后面所有“感觉更好”都没有基线。

评估的作用不是证明系统好，而是：

1. 发现当前排序问题；
2. 给后续优化提供前后对比；
3. 把“答错”拆成检索问题、生成问题、标注问题。

### 1.2 Golden set

新增 `data/eval/golden_set.jsonl`，30 条中文问题：

| category | cases |
|---|---:|
| tutorial | 15 |
| advanced | 4 |
| multi-hop | 3 |
| deployment | 3 |
| how-to | 2 |
| security | 2 |
| version | 1 |

每条字段：

```json
{
  "id": "t01",
  "question": "FastAPI 的第一个应用怎么创建并运行？",
  "expected_urls": ["https://fastapi.tiangolo.com/tutorial/first-steps/"],
  "category": "tutorial",
  "language": "zh"

```

设计考虑：

- 中文提问、英文文档，符合真实使用场景
- 大多数是单跳，少量多跳
- 包含 deployment、security、version，不全是 tutorial
- `expected_urls` 允许一个或多个正确 URL
- 先做 30 条，目标是后续扩到 60–100 条

## 2. HTTP 安全：从“只有 LLM 额度”到“请求、embedding、token 都有闸门”

### 2.1 为什么做

之前的额度锁只锁 LLM chat。

但 `/api/v1/search` 每次都会调用 embedding；`/api/v1/chat` 也会先调用 embedding。

如果公网暴露：

- 别人可以刷 `/search` 烧 embedding 额度
- 没有 per-IP 限流
- 没有 access token

### 2.2 新增限制

```dotenv
RATE_LIMIT_PER_MINUTE=30
EMBEDDING_DAILY_REQUEST_LIMIT=500
EMBEDDING_DAILY_TOKEN_BUDGET=200000
API_ACCESS_TOKEN=
```

实现：

- `security.py`
- Redis 固定窗口限流：`rate:{scope}:{ip}:{minute}`
- 每次 `/search`、`/chat` 先鉴权、再限流、再预占 embedding
- `API_ACCESS_TOKEN` 支持 `Authorization: Bearer` 或 `X-API-Key`
- 前端可选 `VITE_API_TOKEN`
- Redis 不可用返回 503，不绕过
- 429 时记录 quota rejection

### 2.3 验证

真实调用 `/api/v1/search`：

```text
200
```

Redis 中出现：

```text
rate:search:172.18.0.1:...
quota:embedding:requests:20261115
quota:embedding:tokens:20261115
```

说明限流和 embedding 额度都生效。

测试：

- 限流允许 -> 超限 429
- Redis 故障 -> unavailable
- token 缺失/错误 -> 401
- Bearer / X-API-Key 都能识别
- 前端和 API 原有测试全过

### 2.4 重要限制

- `API_ACCESS_TOKEN` 是共享 token，不是用户登录
- 前端 bundle 里的 `VITE_API_TOKEN` 用户可见
- 正式上线仍需要真实账号体系
- 限流按 IP，100 个用户在同一 NAT 下会被一起限流

## 3. SSE 流式：让回答逐字出现

### 3.1 为什么

之前 `/chat` 要等完整答案生成完才返回。

用户体验上：

- 首屏空白时间长
- 长回答看起来像卡住
- 无法先展示 sources

### 3.2 后端

新增：

```text
POST /api/v1/chat/stream
```

事件顺序：

```text
sources -> token × N -> usage -> done
```

异常：

```text
event: error
```

实现：

- `OpenAICompatibleChatClient.stream()` 解析 OpenAI 兼容 SSE
- API 用 `StreamingResponse`
- 先检索，先发 sources，再流 token
- Nginx `/api` 关闭 `proxy_buffering`
- `X-Accel-Buffering: no`
- `usage` 事件当前是 null，因为流式响应不一定返回 usage

### 3.3 前端

- 用 `fetch` + `ReadableStream` 解析 SSE
- 不能用原生 `EventSource`，它只支持 GET
- 处理分块边界：缓冲区按 `\n\n` 切 event
- sources 先渲染，token 增量追加
- error 事件显示错误

### 3.4 验证

通过 Nginx 8080 实测：

```text
status 200
counts {'sources': 1, 'token': 131, 'usage': 1, 'done': 1}
first_token_ms 1854
last_event done
```

后续一次：

```text
counts {'sources': 1, 'token': 125, 'usage': 1, 'done': 1}
first_token_ms 757
```

首 token 在 0.75–1.9 秒之间，满足 <2s 的目标（受模型网络波动影响）。

Playwright 实测：

- 先出现 sources
- 答案逐字出现
- 代码块正常
- `[2]` 引用正常
- deprecated badge 正常

## 4. 多轮会话：Redis 历史 + 前端对话线程

### 4.1 为什么

单轮问答无法处理：

- “那它呢？”
- “和 startup/shutdown 有什么区别？”
- “再给一个例子”

### 4.2 后端

新增 `generation/session.py`：

- Redis key：`chat:session:{session_id}:messages`
- 最多 12 条消息（约 6 轮）
- TTL 7 天
- 只存 `role` / `content`
- session_id 校验：8–64 位字母、数字、`_`、`-`

`ChatRequest` 增加：

```json
{"session_id": "..."}
```

流程：

1. 读历史
2. 检索当前问题
3. `build_messages(query, hits, history)`
4. 生成
5. 保存 user + assistant

system prompt 增加约束：

> 历史只用于理解指代和追问；事实仍来自本轮文档上下文；历史里的 `[n]` 不要和本轮混用。

### 4.3 前端

- `localStorage` 保存 session_id
- 页面显示完整对话线程
- 每轮 assistant 有自己的 sources
- “新对话”生成新 session 并清空页面

### 4.4 验证

API：

```text
r1 200 test-session-multiturn-01
r2 200 test-session-multiturn-01
```

追问：

```text
那它和 startup/shutdown 有什么区别？
```

返回基于上一轮的对比回答。

Redis：

```text
chat:session:test-session-multiturn-01:messages
len = 4
ttl = 604800
```

Playwright 连续两轮：

- 两条用户消息
- 两个回答
- 两套 sources
- Redis 对应 session 4 条消息

### 4.5 限制

- `session_id` 不是登录身份
- 别人拿到 session_id 就能读历史
- 没有 query rewrite，追问检索仍可能偏
- 历史只保留 12 条，超出丢最早轮次

## 6. 观测：request_id、JSON 日志、/metrics

### 6.1 为什么

线上出问题，不能靠猜。

需要知道：

- 哪个请求慢了
- 哪个路径在 429
- LLM 预占了多少 token
- Qdrant/Redis/LLM 是否就绪

### 6.2 request_id

每个请求都有 `X-Request-ID`：

```text
请求头传 verify-request-123
响应头返回 verify-request-123
```

不传则自动生成。

### 6.3 结构化日志

API 日志是 JSON 行：

```json
{"ts":"...","event":"http_request","request_id":"...","method":"POST","path":"/api/v1/chat/stream","status":200,"duration_ms":404.3,"client":"172.18.0.1"}
```

### 6.4 `/metrics`

新增：

```text
GET /metrics
```

Prometheus 文本格式，包含：

- `rag_http_requests_total{method,path,status}`
- `rag_http_request_duration_ms{path,quantile}`（p50/p95）
- `rag_tokens_reserved_total{kind}`（LLM/embedding 预占 token）
- `rag_quota_rejections_total{scope}`

实测：

```text
rag_http_requests_total{method="POST",path="/api/v1/chat/stream",status="200"} 1
rag_tokens_reserved_total{kind="embedding"} 27
rag_tokens_reserved_total{kind="llm"} 4324
```

### 6.5 readiness

`/readyz` 现在报告：

```json
{
  "config": {"ok": true},
  "qdrant": {"ok": true},
  "redis": {"ok": true},
  "llm": {"ok": true, "model": "qwen-flash", "mode": "config_only"}
}
```

- Qdrant / Redis 是真实连接检查
- LLM 只检查 key + model，不发真实 completion，避免每次 readiness 烧额度

### 6.6 限制

- metrics 是进程内内存
- 多 worker 会分裂，需要 Prometheus multiprocess 或每 worker 单独抓取
- 没有 Prometheus/Grafana
- 没有告警
- 没有 LangSmith
- 记录的是预占 token，不是账单金额

## 9. 今天的高并发判断（分析，未实施）

当前配置：

```dotenv
LLM_DAILY_REQUEST_LIMIT=50
LLM_DAILY_TOKEN_BUDGET=300000
RATE_LIMIT_PER_MINUTE=30
```

100 个用户/并发时：

- 50 次/天直接不够
- 一次 chat 预占约 4.3k token，100 次约 430k，超过 300k
- 免费 1M token 大约只够 2 轮 100 人
- 30 次/分钟/IP 会大量 429
- 单 API 进程默认线程池约 40，100 个长连接会排队

所以 100 并发不是“加 worker”就完事，必须先：

1. 买付费 LLM 额度
2. 加全局 LLM 并发队列/信号量
3. 4 workers + Nginx keepalive
4. 提高应用层限额
5. 用 fake LLM 做 100 并发压测，不要直接烧真实额度

LangSmith、Prometheus、Grafana 也讨论了，但今天未实施。

## 10. 今天的核心思考

1. **先有评估，再谈优化。** 5/5 smoke 只能证明链路通，30 条 Recall/MRR 才能发现 reference 和 auth 排序问题。
2. **指标变化要分清是代码变好还是标注变准。** 204 那条是标注修正，不是检索提升。
3. **安全要 fail-closed。** Redis 不可用返回 503，不绕过限流和额度。
4. **流式不是“把完整答案切块”。** 必须从 provider 真流，前端按 SSE 分帧解析。
5. **多轮的记忆和检索要分开。** 历史帮助理解指代，但事实仍必须来自本轮检索。
6. **可复现构建是上线门槛。** 镜像不能依赖“你本机刚好有 dist”。
7. **观测不是奢侈品。** 没有 request_id、错误率、P95、token 指标，线上只能猜。
