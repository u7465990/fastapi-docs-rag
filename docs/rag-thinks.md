父子切分（低难度）（必须）：在 LangChain 中实现有现成路径。使用 ParentDocumentRetriever 配合两个 TextSplitter（一个切父块，一个切子块）即可搭建基础框架。难点在于存储设计：你需要同时管理子块的向量索引和父块的文档存储（如用向量库存子块，用文档数据库或字典存父块），并建立可靠的映射关系。这要求你对系统架构有基本认知。

代码块保护（中等难度）（亮点，最后可以写多少%提升的）：LangChain 原生的 RecursiveCharacterTextSplitter 并不天然理解 Markdown 代码块的语义边界。要实现你描述的保护逻辑，通常需要：

自行编写解析逻辑：用正则或状态机识别 ```` 围栏代码块的起止，确保在切分时将其视为一个不可分割的单元。
或引入外部库：使用 lumberjack-py、chunkana 等专门为 RAG 设计的、代码感知的切分库来替代默认 splitter。
这步的“难”在于你需要走出 LangChain 的舒适区，处理 Markdown 的结构化特性。

标题上下文注入（低到中等难度）：技术上不难。你需要在解析 Markdown 时提取标题层级（Heading Path），并将其与每个 chunk 的内容拼接。真正的“难”在于设计决策：标题前缀是只用于 embedding，还是也存入 payload 供 LLM 参考？这需要你通过评估实验来回答，而不是凭感觉决定。这正是你方案中“具体策略应在评估中对比”这句话的价值所在。

Contextual Retrieval（可选实验，高成本）：用 LLM 为每个 chunk 生成上下文摘要，效果上限更高，但成本也显著增加。对于求职项目，你可以将其作为一个 “可扩展的优化方向” 在文档中提及，并说明你“先评估，再决定是否全量启用”的原则，这本身就能体现良好的工程判断力，而不需要实际跑通全量流程。
（把“标题注入”和“Overlap 调优”作为你“评估驱动开发”的证据：不要只声称你做了，而是展示你如何通过一个小型评测集，对比了“无标题注入 vs 有标题注入”以及“不同 overlap 大小”对 Recall@K 的影响。哪怕提升很小，这个“诊断-干预-验证”的闭环过程，正是面试官对应届生最看重的“研究潜力”的体现。）

## 一句话定位

**BM25 是一个“算分函数”，不是模型，也不是向量。** 它给定一个查询和一篇文档，输出一个相关性分数，用来排序。它属于**稀疏检索 / 词袋模型**家族，和 TF-IDF 一脉相承但更精细。它**不依赖训练、不产生 embedding、不需要 GPU**，本质上就是一个基于**倒排索引**的统计排序公式。

你笔记里那段公式，就是它的全部核心。没有隐藏层，没有注意力机制，就是词频统计加几个平滑项。

---

## 公式拆解：每个部分在干什么

```
score(D, Q) = Σ_{q_i ∈ Q} IDF(q_i) · [ f(q_i,D)·(k1+1) ] / [ f(q_i,D) + k1·(1−b+b·|D|/avgdl) ]
```

把它拆成三个直觉：

| 组件 | 作用 | 直觉 |
| :--- | :--- | :--- |
| **IDF** | 词越罕见，权重越高 | `checkpointer` 只在少数文档出现 → 它是强信号；`the` 到处都是 → 几乎没区分度。公式 `ln(1 + (N−n+0.5)/(n+0.5))` 保证 IDF 永远为正，且罕见词权重增长被对数压制，不会爆炸。 |
| **TF 饱和** | 词出现次数增加，收益递减 | 一个词出现 1 次到 3 次，分数涨得快；3 次到 10 次，涨得越来越慢，趋近上限。`k1` 控制饱和速度（典型 1.2–2.0）。这避免了“长文堆词”刷分。 |
| **长度归一化** | 惩罚长文档 | `b`（典型 0.75）控制惩罚力度。`|D|/avgdl` 越大，分母越大，分数越低。没有它，长文档天然占优，因为词多、命中概率高。`b=0` 完全不归一化，`b=1` 完全按长度惩罚。 |

**关键认知：BM25 的“词袋”意味着它只看词出现没有、出现几次，完全不看词序、不看语义。** `"splitter text character"` 和 `"character text splitter"` 对它来说可能差不多，但 `"RecursiveCharacterTextSplitter"` 和 `"CharacterTextSplitter"` 是两个不同的 token，它分得清——这正是它在技术文档场景的价值。

## 为什么技术文档 RAG 必须用它

你笔记里的三条理由已经说得很准，我再补一层工程直觉：

**1. 精确符号匹配是 dense 的死穴**
`RecursiveCharacterTextSplitter` 和 `CharacterTextSplitter` 在语义上都是“文本切分器”，dense embedding 会把它们编码得非常接近，甚至可能把前者召回成后者。但用户问的是**具体哪一个**。BM25 把标识符当作 token 做精确匹配，`Recursive` 这个词在文档里出现没出现，它一清二楚。

**2. 未登录词 / 新 API 名**
Embedding 模型有词表上限。LangChain 新发布的 API 名，模型训练时没见过，编码质量很差。BM25 不依赖训练语料，**只要文档里出现了这个 token，倒排索引就能命中**。这是它对“快速迭代的技术文档”的天然适配。

**3. 用户行为**
技术文档的用户经常**直接贴报错信息、类名、参数名**来搜。这类查询的本质是“找包含这个符号的页面”，不是“找语义相似的页面”。BM25 就是为这种查询设计的。

## 在你的 LangChain 项目里怎么落地

**最小实现（Python 生态）：**
- `rank_bm25` 库：纯 Python，几行代码就能在内存里建倒排索引，适合原型和评测。
- 或者用 **Milvus 的 sparse vector / 全文检索**、**Elasticsearch** 的 BM25 实现，适合更大规模。

**混合检索的融合方式：**
BM25 和向量检索各返回一个 top-k 列表，用 **RRF（Reciprocal Rank Fusion）** 融合：
```
RRF_score(d) = Σ_{retriever} 1 / (k + rank_retriever(d))    // k 通常取 60
```
RRF 只看**名次**，不看原始分数——因为 BM25 的分数和余弦相似度量纲完全不同，不能直接加权相加。这是工程上最稳妥的融合方式。

**需要注意的坑：**
- **分词器**：BM25 依赖 tokenization。英文技术文档按空白和标点切基本够用，但**代码标识符需要特殊处理**（驼峰 `RecursiveCharacter` 拆成 `recursive` + `character`，下划线 `text_splitter` 拆开），否则精确匹配会漏。LangChain 文档里大量 API 名是驼峰命名，这一点必须处理。
- **BM25 不理解同义词**：用户说“memory 怎么用”和文档写“short-term memory”，BM25 可能匹配不上，dense 能补。这就是为什么**两者必须互补，不能二选一**。

🧩 什么是“稀疏向量 (Sparse Vector)”
在 Qdrant 里，稀疏向量就是一个 (indices, values) 对：indices 是词在词表中的 ID（整数），values 是该词的权重（比如 TF 值）。它和 dense 向量（固定长度的浮点数组）完全不同——稀疏向量只记录“哪些词出现了、权重多少”，大部分维度都是 0，所以叫“稀疏”。

Qdrant 的全文检索（BM25）就是建立在稀疏向量之上的：每个词对应一个或多个维度，维度上的值代表该词在文档中的权重。

✂️ BM25 为什么被“拆开”：客户端算 TF，服务端算 IDF
标准 BM25 公式里有两半：TF（词频） 和 IDF（逆文档频率）。Qdrant 的设计是：

客户端（索引端） 只负责生成 TF 那一半的稀疏向量，把每个词的词频算好，编码成 indices + values 存进去。

服务端（查询端） 在检索时，根据 collection 里实际存储的文档统计信息，实时计算 IDF，再和查询向量里携带的 TF 权重相乘，完成完整的 BM25 打分。

为什么这么拆？ 因为 IDF 依赖整个语料库的统计量（每个词出现在多少文档里）。如果让客户端算 IDF，就得让客户端维护全量文档的统计信息，这在分布式、多租户场景下既笨重又容易不一致。交给服务端算，客户端就只需要关心“这篇文档里每个词出现了几次”，职责清晰，扩展性好。

🔘 modifier: "idf" 是什么
modifier 是 Qdrant 在创建 collection 时给稀疏向量字段设置的一个配置项。"idf" 的意思是：“这个稀疏向量字段在查询时，请服务端自动应用 IDF 加权”。如果不加这个 modifier，Qdrant 就只按你客户端提供的原始权重（纯 TF）做点积，BM25 的分数会失真，因为常见词没有被降权、罕见词没有被升权。

所以配置长这样：

json
"sparse_vectors": {
  "text-bm25": { "modifier": "idf" }
}
这样 Qdrant 在检索时，会自动从存储的文档中统计 IDF，并应用到打分中，客户端完全不需要自己维护 IDF 状态。

⚠️ “索引端和查询端必须使用同一套分词/加权逻辑”
这是整个架构里最容易出错的地方。稀疏向量的本质是 (词ID, 权重)，词ID 来自分词后的词表。如果索引时用一套分词器（比如 FastEmbed 的 Qdrant/bm25，带 stemming、小写化、停用词过滤），查询时用了另一套（比如简单按空格切分），那么：

文档里 "checkpointer" 被 stem 成 "checkpoint"，ID 是 42；

查询时 "checkpointer" 没被 stem，直接按原词去查，ID 对不上 42；

结果就是：这个词完全匹配不上，检索直接失效。

所以“同一套分词/加权逻辑”的含义是：索引和查询必须用同一个分词器配置（同样的 stemming 规则、同样的 lowercase 设置、同样的停用词表），否则 term 的 ID 空间不一致，稀疏向量检索会静默地返回垃圾结果。

💎 放到你的项目里意味着什么
你在 LangChain 文档 RAG 里如果用 Qdrant 做混合检索，BM25 这一路的关键工程决策就是：

选 FastEmbed 的 Qdrant/bm25 作为稀疏向量生成器，索引和查询都调同一个模型，保证分词一致。

collection 的稀疏字段必须带 modifier: "idf"，让服务端算 IDF，否则 BM25 不完整。

测试一个精确 API 名查询（如 RecursiveCharacterTextSplitter），确认稀疏检索能命中——如果分词器把驼峰拆坏了，这里就会暴露。

把这个设计写进项目文档，并说明“TF 在客户端、IDF 在服务端”的分工，以及分词一致性的风险与规避方式，就是一个非常扎实的工程细节，面试官能从中看出你对系统边界的理解，而不只是“调了 API”。
